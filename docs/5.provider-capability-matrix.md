# Provider capability matrix

This interface is not the lowest common denominator, and it is not Stripe with
the names changed. It is the set of flows a typical backend needs where all four
provider families can plausibly implement each one.

The bar: a backend on this interface can change provider. An implementation may
decline a flow and throw `UnsupportedOperationError`, but the feature set is
chosen so that declining is uncommon.

Only Stripe is implemented in the AntelopeJS ecosystem today. The other three
families are paper constraints on the shape — each was checked against its public
API before a proxy was added, and full coverage is expected of none of them.

## The four families

| Family                   | Model                                                      | What it pulls the design towards                                            |
| ------------------------ | ---------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Stripe**               | Intent-based                                               | The reference for the feature set                                           |
| **PayPal**               | Order-based, not intent-based; different capture semantics | The strongest test of whether the abstraction is real                       |
| **Adyen / Checkout.com** | Closest to Stripe                                          | `shopperReference`-style recurring rather than first-class customer objects |
| **Mollie / Mangopay**    | Lighter, redirect-first                                    | Mangopay is wallet-based and the likeliest to decline a flow                |

## The two places the contract bent to fit

These are design changes made _because_ of the four-family audit, not despite it.

### Customers are an identifier, not a profile

PayPal and Adyen have no first-class customer object. PayPal's vault hangs tokens
off a `customer_id` you mint yourself; Adyen's `shopperReference` is a string you
choose. Neither stores an email or a name you can read back.

Modelling `Customer` as a record with retrievable attributes would have made two
of five implementations return a mostly-empty object and quietly break backends
that read `customer.email`. So `Customer` guarantees the identifier and nothing
else, `email` and `name` are documented as write-where-supported, and the
conformance suite asserts only that the identifier round-trips.

What a customer _is_ here is a container for saved payment methods — which is
exactly what `shopperReference` is. The flow survives the audit; the data model
had to shrink to survive it.

### Unsigned webhooks still verify

Mollie does not sign webhooks. The delivery is a payment identifier and nothing
else, and the documented way to trust it is to call the API and read the current
state. Mangopay is similar.

`VerifyWebhook` is therefore specified by its _outcome_ — a normalised event you
can trust — rather than as a signature check. A Mollie implementation fetches the
payment inside `VerifyWebhook` and returns a full event; a Stripe implementation
checks the HMAC and reads the body. Both satisfy the same contract, and a backend
writes one handler.

Had the contract been `VerifyWebhookSignature(body, signature) => boolean`,
Mollie would have had to decline it.

## What is out, and why

### Subscriptions, invoicing, proration, dunning, tax, coupons

The largest single judgement call. Provider subscription objects diverge more
than any other area: billing anchors, proration arithmetic, trial handling,
dunning schedules and tax engines are all different, and several families have no
equivalent at all. An interface over them would be one most implementations
decline.

What _is_ portable is the mechanism underneath: save a payment method, charge it
off-session on your own schedule. A backend selling recurring access runs its own
cycle on `ListPaymentMethods` + `CreatePayment`, and that works on all five.
Filed as a follow-up rather than dropped — if a portable subset emerges, it would
build on saved methods rather than on provider subscription objects.

### Marketplace and split payments

Stripe Connect, PayPal Commerce Platform, Adyen for Platforms and Mangopay's
wallets are incompatible models, not different spellings of one. Connect splits a
charge; Mangopay moves money between wallets it holds; PayPal routes to
merchants. A backend doing this is deep in one provider's model and should use
that provider's own interface.

### Dispute management

An event, not an API. Evidence formats, deadlines and appeal paths differ so much
that a portable submission call would be a wrapper nobody could use. `dispute.opened`
tells a backend to react; responding goes through the provider.

### Payment links and in-person terminals

Payment links are a dashboard feature more than an API one, and terminal
integrations are hardware-bound and provider-specific.

## How this is kept honest

`src/tests/payment.test.ts` ships in the package and runs against whichever
provider module is wired in. It is written against the contract, not against
Stripe's behaviour, and it is what the second provider will be held to.

Most of it needs no fixture and cannot pass without touching a live provider:
session creation, customer lifecycle, idempotency replay, unknown-identifier
errors, webhook signature rejection.

The charge tests need a chargeable test payment method, which has no portable way
to mint — a card is entered by a payer, and every provider publishes its own test
token instead. The provider module supplies one through
`ANTELOPE_PAYMENT_TEST_METHOD`, and those tests skip, visibly and by name, when
it is absent. That is test _data_ supplied at the boundary, not a stub standing
in for provider behaviour.
