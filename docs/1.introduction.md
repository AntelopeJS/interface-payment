# Introduction

`@antelopejs/interface-payment` defines a provider-agnostic payment interface for
AntelopeJS applications. A backend written against it takes payments, refunds
them, saves payment methods and reacts to settlement events without naming a
provider, and can change provider by swapping the module wired underneath.

## What it covers

| Area                        | Functions                                                                                      |
| --------------------------- | ---------------------------------------------------------------------------------------------- |
| Hosted checkout             | `CreateCheckoutSession`, `GetCheckoutSession`                                                  |
| Direct payments             | `CreatePayment`, `GetPayment`, `CapturePayment`, `CancelPayment`                               |
| Refunds                     | `RefundPayment`, `GetRefund`                                                                   |
| Customers and saved methods | `CreateCustomer`, `GetCustomer`, `DeleteCustomer`, `ListPaymentMethods`, `DetachPaymentMethod` |
| Webhooks                    | `VerifyWebhook`                                                                                |

## What it deliberately does not cover

Subscriptions, invoicing, proration, dunning, tax and coupons; marketplace split
payments; dispute _management_; payment links; in-person terminals.

These are where providers diverge most, and modelling them would mean an
interface most implementations could only decline. For recurring access, use
`@antelopejs/interface-subscriptions`: Stripe native billing is recommended with
Stripe. Choose `@antelopejs/payment-subscriptions` explicitly when you need a
generic clock on saved methods and off-session charges. Each subscription must
have one renewal owner; provider-specific billing features remain outside the
portable contract.
[Provider capability matrix](./5.provider-capability-matrix.md) has the reasoning
per feature.

When a backend needs something beyond this contract, it uses the provider's own
interface — `@antelopejs/interface-stripe` for Stripe — alongside this one. That
is the escape hatch, and it is why this interface does not have one of its own:
an escape hatch here would hand back a provider-shaped object and quietly undo
the portability the interface exists for.

## Installation

```bash
pnpm add @antelopejs/interface-payment
```

Add a module that implements it to your Antelope config; this package declares
the contract and ships no provider logic.

## Conventions

These hold across every function, and an implementation that breaks one is
non-conformant.

**Amounts are integer minor units.** `{ value: 1050, currency: "EUR" }` is €10.50.
Never a float: binary floating point cannot represent most decimal amounts, and
providers round differently when you hand them one. `JPY` has no subunit, so
`{ value: 1050, currency: "JPY" }` is ¥1050. `KWD` has three decimal places.
Every derived amount on a `Payment` — `amountCaptured`, `amountRefunded` — is in
the same currency as `amount`.

**Every mutating call takes an idempotency key.** Payments are the canonical case
where a retried request must not do the work twice. Generate one key per
logical operation, store it with your own record, and reuse it on retry: the
provider returns the original result within its provider-defined replay window.
Reads take no key. After expiration, applications must reconcile uncertain
payments with provider records before retrying; a reused key can charge again.

**Provider identifiers are opaque.** `Payment.id`, `Refund.id`, `Customer.id`,
`PaymentMethod.id` and `CheckoutSession.id` are the provider's own strings. Do
not parse them, do not infer a type from a prefix, and do not assume two
providers shape them alike. Correlate with your own records through
`reference` and `metadata`.

**A failed payment is not a thrown error.** `CreatePayment` resolves with a
`Payment` whose status is `failed`; it rejects only when the call itself could
not be made. See [Payments](./2.payments.md).

**Settlement is asynchronous.** Every provider this interface targets settles
some payments after the call returns, and some after the payer has left. A
terminal state is learned from `VerifyWebhook`, not from the payer's return to
your `successUrl`. See [Webhooks](./4.webhooks.md).

## Multi-account setups

Every function takes an optional trailing `provider` argument naming which
configured account to use, for a backend running more than one merchant account
or more than one provider at once. Omit it for the default.

```ts
await CreatePayment(request, key); // default account
await CreatePayment(request, key, "marketplace"); // a named one
```
