# Payments

Two ways to take a payment: a hosted checkout page the provider renders, or a
payment created directly against a method you already hold. Both produce a
`Payment`, and everything after creation — capture, cancel, refund, events — is
the same for either.

## Status

`PaymentStatus` is the normalised lifecycle. Providers report far more states
than this; these are the ones a backend branches on.

| Status            | Meaning                                                       | What to do                            |
| ----------------- | ------------------------------------------------------------- | ------------------------------------- |
| `pending`         | Accepted, nothing outstanding from the payer, not yet settled | Wait for a webhook                    |
| `requires_action` | The payer must be sent to `redirectUrl`                       | Redirect them                         |
| `authorized`      | Funds held, not taken                                         | `CapturePayment` or `CancelPayment`   |
| `succeeded`       | Captured                                                      | Deliver                               |
| `failed`          | Declined, errored, or expired unpaid                          | Map `failure.code` to payer-safe copy |
| `canceled`        | Voided before capture, by you or by the payer abandoning      | Release the order                     |

`succeeded`, `failed` and `canceled` are terminal — `isTerminalPaymentStatus`
classifies them. The rest will change again, either because the payer acts or
because the provider settles.

`redirectUrl` is present exactly when the status is `requires_action`, and
`failure` exactly when it is `failed`. Those are invariants the conformance suite
checks, so you can branch on the status alone.

## Hosted checkout

The provider hosts the page, collects the method and takes the payment. This is
how most backends should take a one-off payment: no card data reaches your
servers, and the provider handles 3DS, wallets and local methods for you.

```ts fragment
import {
  CreateCheckoutSession,
  GetCheckoutSession,
} from "@antelopejs/interface-payment";
import { randomUUID } from "node:crypto";

const idempotencyKey = randomUUID();
await orders.update(orderId, { idempotencyKey });

const session = await CreateCheckoutSession(
  {
    amount: { value: 4999, currency: "EUR" },
    reference: orderId,
    successUrl: `https://shop.example/orders/${orderId}/thanks`,
    cancelUrl: `https://shop.example/orders/${orderId}/cart`,
    description: "Order #1042",
  },
  idempotencyKey,
);

await orders.update(orderId, { sessionId: session.id });
response.redirect(session.redirectUrl);
```

When the payer comes back to `successUrl`, read the session:

```ts
import { GetCheckoutSession, GetPayment } from "@antelopejs/interface-payment";

export async function readOrderPayment(order: { sessionId: string }) {
  const session = await GetCheckoutSession(order.sessionId);
  if (session.payment) {
    const payment = await GetPayment(session.payment);
    // render payment.status
  }
}
```

**The return is a prompt, not a report.** The payer's browser is not a
trustworthy reporter: they can navigate to `successUrl` themselves, close the tab
before the redirect, or lose the connection. Render what `GetCheckoutSession`
says, and fulfil the order from the webhook.

`CheckoutSession.payment` is absent until the provider has created a payment
behind the session, which for some providers is only once the payer has acted.
Providers whose session and payment are one object return the same identifier in
both fields — which is fine, because identifiers are opaque.

## Direct payments

`CreatePayment` takes a payment without a hosted page. Two uses: charging a saved
method with nobody present, and taking a payment through a form you host.

```ts
import { CreatePayment } from "@antelopejs/interface-payment";

export async function chargeSavedMethod(
  orderId: string,
  savedMethodId: string,
  customerId: string,
  idempotencyKey: string,
) {
  const payment = await CreatePayment(
    {
      amount: { value: 4999, currency: "EUR" },
      reference: orderId,
      paymentMethod: savedMethodId,
      customer: customerId,
      offSession: true,
    },
    idempotencyKey,
  );
  return payment;
}
```

`offSession` says nobody can be prompted. The provider will not return
`requires_action`; it declines instead. Leave it unset when the payer is at the
keyboard, and pass a `returnUrl` so they can be sent through authentication.

### A decline is a result, not an exception

```ts fragment
const payment = await CreatePayment(request, idempotencyKey);

if (payment.status === "failed") {
  logger.warn({ failure: payment.failure }, "payment declined");
  return render("payment-failed", {
    reason:
      "The payment could not be completed. Please try another payment method.",
  });
}
```

`PaymentFailure.message` is for server logs, not for the payer. Use your own
customer-facing copy, optionally selected by `failure.code`; do not expose the
provider's message or `providerCode` in the response.

`CreatePayment` rejects only when the call itself could not be made — bad
credentials, a malformed request, an unreachable provider. A card declined by the
issuer is a `Payment` with status `failed` and a populated `failure`.

This is deliberate. The same decline can arrive synchronously from `CreatePayment`
or asynchronously as a `payment.failed` event, depending on the provider and the
method. Modelling one as an exception and the other as an event would mean
writing the handling twice and keeping the two in step. Instead both give you a
`Payment` with the same shape, so one function handles both.

`PaymentFailure.code` is coarse on purpose — `declined`, `insufficient_funds`,
`expired_card`, `incorrect_details`, `authentication_failed`, `canceled_by_payer`,
`expired`, `processing_error`. Providers report hundreds of decline reasons under
incompatible names, and a backend acts on very few of them. The provider's own
code travels verbatim in `providerCode` for a support ticket.

### Authentication and 3DS

There is no separate mechanism for 3DS or SCA. A payment that needs the payer to
authenticate comes back `requires_action` with a `redirectUrl`, which is the same
redirect the hosted flow uses:

```ts fragment
if (payment.status === "requires_action") {
  return response.redirect(payment.redirectUrl!);
}
```

Any payment can turn out to need it, which is why `returnUrl` is required unless
`offSession` is set.

## Authorize now, capture later

Set `authorizeOnly` to hold funds without taking them — the usual shape for
physical goods, where you charge on dispatch.

```ts
import {
  CapturePayment,
  CreatePayment,
  type Amount,
} from "@antelopejs/interface-payment";

export async function authorizeThenCapture(
  amount: Amount,
  orderId: string,
  paymentMethod: string,
  idempotencyKey: string,
  captureKey: string,
) {
  const authorized = await CreatePayment(
    {
      amount,
      reference: orderId,
      paymentMethod,
      offSession: true,
      authorizeOnly: true,
    },
    idempotencyKey,
  );
  // authorized.status === "authorized", authorized.amountCaptured.value === 0

  const captured = await CapturePayment(authorized.id, captureKey, {
    value: 3999,
    currency: "EUR",
  });
  return captured;
}
```

Omit the amount to capture everything authorized. Capturing less releases the
remainder: there is no second capture against the same authorization here,
because not every provider allows one. If you need to capture in instalments,
authorize per instalment.

`CancelPayment` voids an uncaptured payment and releases the hold.

Authorizations expire — after days, and by a rule that differs per provider and
per card network. Capture promptly, and treat an expired authorization as a
`payment.canceled` or `payment.failed` event rather than assuming the hold lasts.

## Refunds

```ts
import { RefundPayment, type Payment } from "@antelopejs/interface-payment";

export async function refundPart(payment: Payment, idempotencyKey: string) {
  const refund = await RefundPayment(
    {
      payment: payment.id,
      amount: { value: 700, currency: "EUR" },
      reason: "requested_by_customer",
    },
    idempotencyKey,
  );
  return refund;
}
```

Omit `amount` to refund everything not yet refunded. Several partial refunds
against one payment are allowed, up to the captured amount; `Payment.amountRefunded`
tracks the running total, so the remaining refundable amount is
`amountCaptured.value - amountRefunded.value`.

**Refunds settle asynchronously on every provider this interface targets**, so
the usual result of `RefundPayment` is a `Refund` with status `pending`. The
terminal state arrives as a `refund.succeeded` or `refund.failed` event. Do not
treat the call returning as the money having moved — a refund can still fail
after being accepted, and a backend that credits the customer on the call alone
will occasionally credit them for a refund that never landed.

`RefundStatus` is `pending`, `succeeded` or `failed`. `Refund.failure` is present
exactly when the status is `failed`.

`RefundReason` is `duplicate`, `fraudulent`, `requested_by_customer` or `other`.
Providers that have no reason field take it as a note; providers that have one
map the first three onto it. Either way the reason is for the provider's records
and your own, not for the payer.

## Errors

| Error                       | When                                                                                                                       |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `PaymentNotFoundError`      | No record under that identifier, including one the provider cannot parse                                                   |
| `CustomerNotFoundError`     | No customer or payment method under that identifier                                                                        |
| `InvalidPaymentStateError`  | Well-formed, but not applicable to this payment's state — capturing something not authorized, refunding more than captured |
| `WebhookVerificationError`  | A delivery's signature does not verify                                                                                     |
| `UnsupportedOperationError` | The provider does not offer the operation at all                                                                           |
| `PaymentError`              | The base class; every error above is one                                                                                   |

`UnsupportedOperationError` should be rare — the feature set is chosen so a
typical backend never meets one. An implementation that raises it says so in its
README, and raises it for every call to that function, never conditionally.
