# Customers and saved payment methods

A customer is a container the provider associates saved payment methods with.
Save a method once, charge it later with nobody present.

This is what makes recurring billing portable without modelling subscriptions: a
backend selling monthly access saves a method, runs its own billing cycle, and
charges off-session each period. That works on every provider here. A provider's
own subscription object does not — see the
[capability matrix](./5.provider-capability-matrix.md).

## Only the identifier round-trips

```ts
const customer = await CreateCustomer(
  { email: user.email, name: user.fullName },
  idempotencyKey,
);
await users.update(user.id, { paymentCustomerId: customer.id });
```

Store the identifier against your own user record. **Do not read the payer's
details back out of the provider.** `email`, `name` and `metadata` are stored
only by providers that have a first-class customer object; PayPal's vault and
Adyen's `shopperReference` treat the identifier as a key they hang tokens on and
store nothing else, so `GetCustomer` there returns the identifier alone.

The conformance suite asserts the identifier round-trips and nothing more, which
is exactly the guarantee the contract makes. `GetCustomer` is for confirming a
customer still exists, not for reading a profile you did not store yourself.

## Saving a method

A method is saved as a side effect of a payment, not by a call of its own — no
provider here lets you vault a card without the payer presenting it.
`savePaymentMethod` sits on both payment paths and requires `customer` on either.

Through hosted checkout:

```ts
const session = await CreateCheckoutSession(
  {
    amount,
    reference: orderId,
    successUrl,
    cancelUrl,
    customer: user.paymentCustomerId,
    savePaymentMethod: true,
  },
  idempotencyKey,
);
```

On a direct payment, the same flag:

```ts
const payment = await CreatePayment(
  {
    amount,
    reference: orderId,
    paymentMethod: presentedMethod,
    customer: user.paymentCustomerId,
    savePaymentMethod: true,
    returnUrl: "https://shop.example/payment-return",
  },
  idempotencyKey,
);
```

Set `returnUrl` to your application's return route even when charging a saved
method on-session. If the result is `requires_action`, redirect the payer to
`payment.redirectUrl`, then read the payment on the server after they return.

Either way the method appears in `ListPaymentMethods` once the payment reaches
`succeeded` or `authorized` — not at session creation, not when the payer
returns, and not as soon as `CreatePayment` resolves. Settlement is
asynchronous; list after the payment has settled, or after the
`payment.succeeded` event.

## Charging off-session

```ts
const [method] = await ListPaymentMethods(user.paymentCustomerId);
if (!method) return dunning.noMethodOnFile(user);

const payment = await CreatePayment(
  {
    amount: { value: 999, currency: "EUR" },
    reference: `sub-${user.id}-${period}`,
    customer: user.paymentCustomerId,
    paymentMethod: method.id,
    offSession: true,
  },
  `renewal-${user.id}-${period}`,
);
```

The idempotency key is derived from the billing period, so a retried or
duplicated renewal job replays within the provider-defined replay window.
After expiration, reconcile uncertain payments before retrying: the same key
may create another charge.

An off-session charge can still fail — the card expired, the bank wants the payer
to authenticate, there is no money. It comes back `failed`, never
`requires_action`, because there is nobody to send anywhere. Handle it by asking
the payer to return and pay on-session.

## What a saved method tells you

```ts
export interface PaymentMethod {
  id: string;
  type: "card" | "wallet" | "bank_account" | "other";
  customer: string;
  card?: CardDetails;
  createdAt: number;
}
```

`card` is present when `type` is `card`: brand, last four digits, expiry month
and year. Enough for a payer to recognise which card they saved, and nothing
more — never the PAN, and never a token you could charge outside the provider.

A PayPal vault entry is a `wallet` and carries no `card`. Branch on `type` rather
than assuming `card` is there.

## Removing

`DetachPaymentMethod` removes one method and leaves the customer.
`DeleteCustomer` removes the customer and detaches every method saved against it.
Payments already taken are unaffected and stay readable by their identifiers —
deleting a customer is not a way to erase a payment history, and refunds against
past payments keep working.
