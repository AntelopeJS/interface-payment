# Webhooks and events

Every provider this interface targets settles some payments asynchronously. A
backend that reads only what its own calls return will report a payment pending
that succeeded twenty minutes ago. Webhooks are not optional here — they are the
only way to learn a terminal state.

## Verifying a delivery

```ts
import { VerifyWebhook, WebhookVerificationError } from "@antelopejs/interface-payment";

@Post()
async webhook(@RawBody() body: Buffer, @Headers() headers: Record<string, string>) {
  let event;
  try {
    event = await VerifyWebhook({ body, headers });
  } catch (error) {
    if (error instanceof WebhookVerificationError) return new HTTPResult(403, "Unauthorized");
    throw error;
  }

  if (!event) return new HTTPResult(200, "Ignored");

  await handle(event);
  return new HTTPResult(200, "OK");
}
```

`WebhookRequest.body` is typed `Uint8Array` rather than `Buffer` so this
package's published types carry no ambient Node dependency — a consumer
compiling without `@types/node` would otherwise fail inside `node_modules`. A
Node `Buffer` is a `Uint8Array`, and is what an HTTP handler hands you, so pass
it straight through.

**The body must be the raw bytes.** Signature schemes cover the bytes as sent, so
a body that has been through `JSON.parse` and re-serialised will not verify —
key order and whitespace change. Use a raw body handler on this route.

Three outcomes, and they are distinct on purpose:

| Outcome                    | Meaning                                    | Respond             |
| -------------------------- | ------------------------------------------ | ------------------- |
| A `PaymentEvent`           | A genuine delivery this interface models   | 200, after handling |
| `undefined`                | Genuine, but not one of the modelled types | 200                 |
| `WebhookVerificationError` | Could not be established as genuine        | 403, act on nothing |

**"Genuine" is not always a signature check.** Stripe, Adyen and PayPal sign, so
verification is the signature over the raw bytes. Mollie and Mangopay do not
sign: the delivery is a bare record identifier, and the implementation
establishes it by reading that record back from the provider. A body naming no
record, or one the provider will not confirm, raises `WebhookVerificationError`
on those providers just as a bad signature does on the others. Your handler is
the same either way — which is the point.

### Where an event's fields may come from

This is the part that bites, and it is a rule for implementations rather than
for callers.

**Every field of the returned event must come from data the implementation has
authenticated.** Establishing a delivery and populating an event are two steps,
and the first proves different things on different providers:

| Style                          | What establishing proves     | What the event may be built from |
| ------------------------------ | ---------------------------- | -------------------------------- |
| Signed (Stripe, Adyen, PayPal) | The whole body is authentic  | The body                         |
| Re-fetched (Mollie, Mangopay)  | A record with that id exists | **The record read back, only**   |

A re-fetch proves the identifier. It proves nothing about any other field in the
body — not the event type, not the amount, not the status. So on a re-fetch
provider the body is a pointer and nothing else: the event's `type`, the kind of
record it is, and every field of `payment`, `refund` or `dispute` come from the
record that was read.

The failure mode is writing a re-fetch provider by analogy with a signed one,
which is what a careful implementer does. Mangopay's delivery carries
`RessourceId`, `EventType` and `Date`, and `EventType` maps neatly onto
`PaymentEvent.type` — so an implementation that re-fetches to establish the
delivery and then reads `EventType` from the body accepts an unauthenticated
payment-state forgery. Anyone who can reach the endpoint posts a real payment id
with a succeeded event type; the read confirms the id exists; verification
passes; the backend ships goods for a payment the provider's own record says is
pending or failed.

Mollie is safe here by accident rather than by design — its body is only
`id=tr_xxx`, so there is nothing else to trust even if an implementer wanted to.
Mangopay is the live case, and a provider added later is the general one.

The `undefined` case is the common one. Providers send dozens of event types —
account updates, payout notifications, report completions — and an interface that
threw on all of them would make every implementation reject genuine traffic,
which providers answer by retrying for days. Verified-but-unmodelled is a normal
result, not a problem.

## The event set

```ts
"payment.pending"    "payment.authorized"  "payment.succeeded"
"payment.failed"     "payment.canceled"    "refund.succeeded"
"refund.failed"      "dispute.opened"
```

The `payment.*` types are exactly the `PaymentStatus` values a backend learns
about asynchronously. `requires_action` has no event because it is known
synchronously, from the call that created the payment — no provider tells you
later that a payer needs to authenticate.

`payment.canceled` covers abandonment and expiry, not just a `CancelPayment` you
made yourself. An abandoned checkout is the most common outcome of a hosted
session, and without this event a backend leaks orders that sit pending forever.

`payment.authorized` is what tells an auth-then-capture backend that the hold
landed. Without it the auth/capture flow would only work synchronously, which on
a redirect-first provider means not at all.

Exactly one of `payment`, `refund` and `dispute` is set, matching the type
prefix, and it carries the object's state at the moment the provider sent it.

## Handling

```ts
const HANDLERS = {
  "payment.succeeded": (event) => orders.fulfil(event.payment!.reference),
  "payment.failed": (event) => orders.declined(event.payment!.reference),
  "payment.canceled": (event) => orders.release(event.payment!.reference),
  "payment.authorized": (event) => orders.readyToShip(event.payment!.reference),
  "payment.pending": (event) =>
    orders.awaitingSettlement(event.payment!.reference),
  "refund.succeeded": (event) => refunds.settled(event.refund!.id),
  "refund.failed": (event) => refunds.retry(event.refund!.id),
  "dispute.opened": (event) => disputes.open(event.dispute!),
};

async function handle(event) {
  if (await events.seen(event.id)) return;
  await HANDLERS[event.type]?.(event);
  await events.record(event.id);
}
```

Two rules, and both bite in production:

**De-duplicate on `event.id`.** Providers redeliver. A delivery your handler
acknowledged can arrive again because the acknowledgement was lost, and a
handler that ships an order twice is a real loss.

**Do not assume an event is newer than what you hold.** Providers deliver out of
order, and a `payment.pending` can land after the `payment.succeeded` for the
same payment. Guard on your own record's state, or re-read with `GetPayment`
before acting on a transition backwards.

## Disputes

`dispute.opened` reports that a payer has challenged a captured payment, so a
backend can react — hold the goods, notify someone, flag the account.

Responding to a dispute is not modelled. The evidence a provider wants, the
format, the deadlines and the appeal path differ so much between them that an
abstraction would be a thin wrapper nobody could use portably. Respond through
the provider's own interface or its dashboard.
